# Combat Map: a DM-only virtual tabletop

Working guide for this repository, for humans and AI agents. It is authoritative here: `CLAUDE.md` files in parent directories describe other projects and do not apply. The product spec is [docs/SPEC.md](docs/SPEC.md) (verbatim apart from a two-line preface); this file records how it is being built and every decision that refines or deviates from it. **Update it at the end of every milestone** (status table, architecture, decisions).

## What it is

A static-site virtual tabletop for D&D 5e combat with exactly one user, the DM, and two same-origin windows:

- `#/dm`: the editor. Owns the full `CampaignState` and every tool.
- `#/player`: the presentation window on a TV, projector or screen-share. Renders only `PlayerViewState` received over `BroadcastChannel('vtt-sync')`, and never writes state.

State lives in the DM's browser (IndexedDB) and can be synced to a GitHub Gist with a personal access token. No backend, no accounts, no runtime network calls except the GitHub API. UI language: English.

## Projection rule (the security boundary)

> **The player window never receives data it should not render.** Not "receives and hides": never receives.

- `projectForPlayers(campaign, ui, devicePrefs): PlayerViewState` (pure, `src/projection/`, milestone 4) is the only producer of campaign-derived data for the player window. Other sync messages carry no campaign data, except a ping's `x, y`.
- **Whitelist, never spread.** Build every output object as an object literal, field by field. Never `...token`, never return a filtered or mapped campaign array, never pass campaign objects through. A field added to `Token` later must not reach players unless someone adds it to the projection on purpose.
- The player types in `src/state/types.ts` are dedicated types that never reuse campaign types. That catches extra keys only in object literals: TypeScript does **not** catch a spread or a passed-through object. The real guard is the tests below.
- DM-only means **every field not in `PlayerViewState`**. In particular: `name` of items, tokens, scenes and assets; `hidden`; `dmNotes`; `hp.current`/`hp.max`; token `kind` (npc vs enemy is a spoiler); initiative values, tiebreaks and modifiers.
- What is removed (SPEC §3, §5.6–§5.9):
  - hidden items on every layer (`hidden: true`), and every item on a layer whose `layerState.visible` is false;
  - with fog on, enemy and NPC tokens that are not currently visible (nine-point footprint test), including those in explored-but-dim areas. Player tokens are always sent. Props in explored areas are sent; props in unexplored (black) areas are not;
  - vision circles of tokens that are not vision sources. A vision source is a non-hidden token on a visible tokens layer, with `visionFt > 0`, that is a player (or an NPC when `settings.npcVision`). One selector in `src/geometry` decides this for both fog rendering and the projection;
  - initiative entries whose effective visibility is hidden (`'hidden'`, or `'auto'` while the linked token is missing, hidden or on a hidden layer), with no placeholders; the whole tracker unless `visibleToPlayers`; values always. `PlayerToken.active` (the pulsing ring) is true only when the tracker is shown and the active entry is effectively visible. Entry names are player-facing by definition (see `InitiativeEntry.name`); `hpFraction` is sent only for public HP bars;
  - HP numbers (only `hpFraction` when `hp.publicBar`), labels unless `showLabel`;
  - the ruler unless `settings.shareRuler`; when shared it is sent as points plus precomputed feet and cells. Templates with `visibleToPlayers: false`; players never get affected-square counts;
  - during blackout, everything: the view is `{ blackout: true, splashAssetId }`, and pings are not sent.
- **Drags.** Fog vision uses **committed** positions: vision does not move while a token is dragged (SPEC §5.6 reveal timing). Player tokens are shown at their live drag position. An enemy or NPC token is shown at its live position only while that position is itself visible under the committed vision; otherwise it is omitted until the drop.
- **Map images are the deliberate exception.** The player loads the whole map blob and fog covers the unexplored parts, so fog rendering must fail closed: the player fog layer starts as an opaque black rectangle over the viewport and explored/visible regions are cut out of it (`destination-out`). Unexplored parts are never "painted black" afterwards, and a new scene's map appears only once its fog is ready.
- The player window reads asset blobs from IndexedDB only through `src/persistence/assetBlobs.ts`, by the ids it was sent, and never loads the campaign. Lint (`.oxlintrc.json`) blocks direct imports from `src/player/**` and `src/canvas/**` of `dm`, `panels`, `tools`, `gist`, `store`, `app/App` and every `persistence` module except `assetBlobs`; `src/architecture.test.ts` checks the transitive import graph from `PlayerApp` and that both windows are lazy-loaded chunks. An e2e test checks the player page never requests the DM chunk.
- Both windows share one origin and one event loop, and the player window has `window.opener`. The boundary is therefore code discipline enforced by the checks above, not process isolation. Player code must never touch `window.opener`.
- Tests (required before milestone 4 is done): fill **every** string and number field of a sample campaign with unique canaries and assert that only whitelisted values appear in `JSON.stringify(projectForPlayers(...))`; one test per case above (hidden, fogged, hidden vision source, live drag into darkness, blackout, initiative visibility and `active`, HP, ruler, templates); an exact-key test per player type that fails when a new field appears. SPEC §9's e2e "hidden token is absent from the player view" is a milestone 4 done-criterion.

## Data model

Source of truth: [`src/state/types.ts`](src/state/types.ts) (documented field by field). Summary:

- `CampaignState { version, id, name, scenes[], activeSceneId, sceneMemory, library: AssetMeta[], settings, presentation, createdAt, updatedAt }`
- `Scene { id, name, grid, layers { map: Item[], props: Item[], tokens: Token[] }, layerState, fog { enabled, exploredEnabled, manual }, initiative, templates: AoeTemplate[] }`
- `sceneMemory: Record<sceneId, { explored: FogMask, playerView: ViewRect | null }>`: per-scene state that undo must never touch, kept outside `scenes`. Created with its scene; kept when the scene is deleted (so undo restores it intact) and dropped by `validateCampaign` on the next load once its scene is gone.
- `Item { id, assetId, name, x, y, width, height, rotation, locked, hidden, opacity }`: center-anchored, world px, rotation in degrees clockwise about the center.
- `Token extends Item { kind, sizeCategory, visionFt, label, showLabel, badge, hp, conditions, color, dmNotes, initiativeModifier }`; `badge` is the 1–3 characters drawn on built-in "initials" tokens.
- `AssetMeta { id, kind, name, tags, mime, width, height, bytes, hash, defaultSize, defaultKind, defaultCells, localOnly, createdAt }`: an uploaded image (`library`), describing exactly the stored blob.
- `FogMask { cellPx, chunks }`: sparse chunked bitmap (base64 per 64×64-cell chunk, trailing zero bytes omitted).
- `Initiative { entries, activeEntryId, round, visibleToPlayers }`; entries carry `value`, `dexTiebreak`, `manualOrder`, `visibility: 'auto' | 'hidden' | 'shown'`.
- `Presentation { cameraMode, blackout, splashAssetId }`. `Camera { x, y, zoom }` is the DM window's camera; views shared with players are `ViewRect { x, y, width, height }` (world px), which the player fits to its own screen.
- Transient (never persisted): `UiState` (tool, selection, DM camera and viewport size, ruler, temporary template, preview-as-players, live drag positions) and `Ping`.
- Player side: `PlayerViewState` = `{ blackout: true, splashAssetId }` or `{ blackout: false, scene: PlayerViewScene }`, built only from the `Player*` types.

Rules: plain JSON only (no classes, Maps, typed arrays, Dates); persisted data has no optional keys (absent values are `null`); array order is z-order and scene order. Factories live in `src/state/defaults.ts` (`createCampaign`, `createScene`, `createSceneMemory`).

### Schema changes

Every persisted campaign carries `version`; [`src/state/migrations.ts`](src/state/migrations.ts) upgrades old documents one version at a time. `migrateToCurrent` checks only the version: every load, import and gist pull must also run `validateCampaign` ([`src/state/validate.ts`](src/state/validate.ts)), which rebuilds the document field by field as fresh object literals (unknown keys dropped, ids that name `Object.prototype` members rejected), checks types, enums, finite numbers, ranges, hex colors, id uniqueness and references, and repairs a few benign inconsistencies (Decision 49). A new field must be added to the validator, or it is silently dropped on load.

**Schema v1 is frozen since milestone 3**, the first version that saves campaigns (in the DM's browser). Every change to the persisted shape follows every step:

1. bump `CURRENT_SCHEMA_VERSION` and add `MIGRATIONS[old]` (pure JSON → JSON, no app imports);
2. update `src/state/types.ts`, `defaults.ts`, the validator and `fixtures/sampleCampaign.ts` to the new shape. A field added in v*N* must hold, in the sample, exactly the value `MIGRATIONS[N-1]` produces from the old sample; test other values in separate unit tests;
3. add the new frozen fixture (run from the repo root; `sampleCampaign.ts` may only use `import type`): `node -e "import('./src/state/fixtures/sampleCampaign.ts').then(m=>process.stdout.write(JSON.stringify(m.sampleCampaign,null,2)+'\n'))" > /tmp/v.json && mv /tmp/v.json src/state/fixtures/campaign.v<new>.json`;
4. never edit committed `campaign.v*.json` files once a version has shipped. The test suite migrates every one of them and expects the current sample.

## Architecture

Planned design for the whole project. Items marked (M*n*) are built in that milestone; refine them here when they are built.

- **Coordinates.** World px = map pixels at scale 1. Grid cell (i, j) spans `[offsetX + i·size, offsetX + (i+1)·size)`. A token's footprint is `FOOTPRINT_CELLS[sizeCategory]` cells and its `width`/`height` always equal footprint × `grid.size` (rewritten when the size category or grid size changes; the Transformer only rotates tokens). Odd footprints snap the center to cell centers, even ones to grid intersections. Props snap per axis on their axis-aligned footprint (w/h swapped at 90° and 270°, the rotated bounding box otherwise): the nearer edge moves onto a grid line, which for whole-cell spans puts odd spans on cell centers and even spans on intersections (`src/geometry/snap.ts`). Resizing snaps the dragged Transformer anchor to grid lines (single item at a multiple of 90° only). Dragged tokens always snap to their cells; dragged props snap magnetically (within 25% of a cell); placement always snaps; nudges never do; Alt disables snapping (Decision 48). Feet = cells × `feetPerCell`.
- **State (M2, M3).** Zustand stores in `src/store/` (DM only; the player can never import them): `campaign.ts` (the persisted `CampaignState` plus `past`/`future` history; it starts as `campaign: null` and the DM session loads one), `ui.ts` (`UiState` plus DM-only bits: hover, context menu, clipboard, notice, open dialog, per-scene cameras) and `session.ts` (lock phase, save status, local campaign list), later `sync`/`gist` status. Scene list actions are in `sceneActions.ts`, library actions in `libraryActions.ts`. Every change to `scenes`/`name` goes through `commit(label, recipe, { coalesceKey })` (Immer `produceWithPatches`); other fields through `setUnrecorded`. Editing actions live in `actions.ts`, pure history logic in `history.ts`. Undo history keeps `{ patches, inversePatches, label, coalesceKey, time, sceneBefore, sceneAfter }` entries (cap 200); a drag commits once on drop, and consecutive commits with the same coalesce key within 1 s merge (sliders, color pickers, repeated nudges). History records `scenes` and `name` only; `sceneMemory`, `presentation`, `settings`, `library`, `activeSceneId` and `updatedAt` are changed outside recorded actions, or inside a recorded recipe where the change applies but is never undone (a new scene's memory, switching to it). Undo shows `sceneBefore` and redo `sceneAfter` when they exist, and `activeSceneId` always names an existing scene (Decision 51). A subscription in the session reacts to `activeSceneId` changes (`sceneSwitched`: remember the old scene's camera, restore or fit the new one, clear the selection). Undo covers fog toggles, manual fog edits, initiative edits and turn changes. Replacing the campaign (load, import, gist pull) clears history; deleting an in-use asset (after the spec's warning) removes its items and clears history, since the blob cannot come back. **No import-time side effects** in DM modules: stores are created empty, and the session (`src/dm/session.ts`: Web Lock, IndexedDB load, autosave, BroadcastChannel) starts from a `DmApp` effect, once per page. Components subscribe with narrow selectors that return existing references or primitives (a zustand 5 selector returning a new object loops forever). Drags are pointer gestures in `src/dm/canvas/DmCanvas.tsx`, not Konva `draggable`: each move writes `ui.liveDrag`, items render at their live position, and the drop commits once. A store subscription in `DmApp` prunes the selection after every campaign change.
- **Rendering (M2, M4, M5).** One react-konva `Stage` per window. As built in M2 the DM stage has three Konva layers: the map layer (its own canvas, so dragging tokens never redraws an 8k map; `listening` only while unlocked), a content layer (the grid, then props and tokens as groups with per-layer `visible`/`listening`), and the overlay (hover and locked-selection outlines, hidden/locked badges, drag ghost + path + distance, `Transformer`, marquee, calibration box). Templates, ruler, pings and fog join the overlay side in later milestones. The grid sits above the map and below props, and does not follow layer visibility. Map images are **not** `cache()`d (an 8k map at DPR 2 hits Chrome's maximum canvas area and caching a single bitmap gains nothing): the locked map layer is `listening(false)`, images use `perfectDrawEnabled(false)` and are decoded once. `cache()` is only for groups of many vector shapes, with an explicit `pixelRatio` and a size guard. The grid is one custom `Shape` drawing only the lines in view. Renderers in `src/canvas/` take props only and are shared: the DM canvas (wired to the store in `src/dm/`) adds DM decorations (hidden badge, fog tint); the player canvas renders `PlayerViewState`; "Preview as players" renders `projectForPlayers(...)` through the player renderer inside the DM window, so it matches by construction. Transformer: `keepRatio={false}` so Shift keeps the ratio; Konva always scales about the center while Alt is held, which we accept (Alt also disables snapping). Heavy work (downscaling, hashing, base64, fog rasterizing) runs in Workers, because both windows share one event loop and a long DM task freezes the TV.
- **Sync (M4).** `src/sync/` owns a typed protocol on `BroadcastChannel('vtt-sync')`, every message tagged `{ v: 1, type }`. Player → DM: `hello { clientId }` on load, `bye` on `pagehide`. DM → player: `view` (a full `PlayerViewState`, sent on `hello`, on change, and at most every 50 ms while dragging; it carries a fog revision so the player re-rasterizes only when fog changed) and `ping { id, x, y, sceneId }` (the player times it on receipt). Presence uses Web Locks, not timers (background tabs throttle timers to once a minute): the DM holds `vtt:dm` for its lifetime and the player holds `vtt:player`; each side learns the other is gone when its pending request for the other's lock is granted. The player shows "connecting…" only before its first view; afterwards it keeps the last frame with a small "DM disconnected" badge. The DM shows toasts on player connect/disconnect.
- **Single DM window (M3).** Only the tab holding the `vtt:dm` Web Lock loads, edits, autosaves, and later syncs gists and broadcasts. At startup a tab asks for the lock (`ifAvailable`, then waits up to 1 s, because after a reload the old page may still hold it); without it, it shows "already open in another tab" with "Use this tab instead". Taking over posts `release-request` on `BroadcastChannel('vtt-dm')` (no campaign data): the holder flushes its autosave, unloads the campaign, releases the lock and shows "now open in another tab"; if it does not answer within 3 s the new tab steals the lock (`steal: true`), and the old one drops out when its lock request rejects (Decision 57).
- **Assets (M2, M3).** Built-in assets are generated SVGs in a code registry (`src/assets/builtin/registry.ts`) with stable ids `builtin:<kind>/<slug>`; they are never stored or uploaded. Props and maps are rasterized once into canvases (`src/assets/images.ts`; props at 256 px per cell), so Konva never re-rasterizes SVG while panning. Tokens are Konva shapes: a disc in `Token.color` with `Token.badge` as text (initials tokens) or a glyph plus a number pip; library "presets" (name, kind, size, look) sit on top of the token asset ids. Uploads (PNG/JPEG/WebP, sniffed by magic bytes) are finalized at import in a module worker (`src/assets/upload/imageWorker.ts`, rules in `plan.ts`): decoded with EXIF orientation applied, downscaled to ≤ 8192 px on the long side (with a notice), re-encoded to WebP if over the 7 MB gist limit, hashed (SHA-256), thumbnailed (256 px), and stored as blobs in IndexedDB under a random id, so `AssetMeta` always describes exactly the blob that is stored and synced. If still too large, the asset is `localOnly` (Decision 55). `src/assets/catalog.ts` resolves built-in and uploaded assets for placement; `src/assets/images.ts` decodes uploads once into an `ImageBitmap` read through `persistence/assetBlobs`. Uploaded token images are drawn cropped to a circle inside the ring color (Decision 56).
- **Persistence (M3).** `idb` database `vtt` (schema and `getAssetBlob` in `src/persistence/assetBlobs.ts`, the only persistence module the player may import; DM access in `db.ts`) with stores `campaigns` (id → raw campaign JSON), `assets` (id → Blob), `thumbnails` (id → Blob, derived, never synced) and `meta` (last campaign id; later the remembered PAT and gist sync records). Several local campaigns, managed in the Campaigns dialog (rename, new, open, duplicate, delete). Asset blobs are shared between campaigns and garbage-collected by reference (Decision 52). Autosave (`autosave.ts`, pure scheduling) writes 1 s after the last change and when the page is hidden, one write at a time, with a "Saved / Unsaved changes / Saving / Not saved, retry" indicator; a write started during unload is aborted, so leaving with unsaved changes asks "Leave site?" (Decision 58). Quota errors show a clear message (export and gist sync join it in M8). Load = `migrateToCurrent` + `validateCampaign`; a campaign that fails stays stored untouched and the DM gets a recovery screen. `navigator.storage.persist()` is called after the first save; Settings shows its result, the usage estimate and the number of `localOnly` images (the backup reminder joins in M8; Safari may still evict storage after 7 days without a visit, so backups are the real protection). If IndexedDB cannot be opened the session runs in memory with a "Not saving" indicator.
- **Fog (M5).** Visible area = union of circles around vision sources (see Projection rule) at committed positions, plus manual edits applied in order (`reveal` = fully visible, `hide` = black). Explored memory (in `sceneMemory`) grows by every committed change to the visible area while players can see the scene (fog and explored memory on, no blackout): a drag adds the capsule swept from origin to destination; nudges, paste, placement, unhide and `visionFt`/`kind`/`npcVision` changes add the new circles. During blackout nothing is recorded; lifting blackout records the current circles. If the grid is calibrated while the mask is still empty, recreate it at the new quarter-cell size; otherwise keep its `cellPx`. A token counts as visible if any of nine sample points of its footprint (center, corners, edge midpoints) is visible. The player window renders fail-closed (see Projection rule): black outside explored areas, dim over explored-but-not-visible ones, clear inside visible ones. The DM window shows the same regions as a light tint.
- **Gist (M8).** `fetch` to the GitHub REST API with the PAT and `cache: 'no-cache'` on every GET (API responses are cacheable for 60 s). Files: `vtt-manifest.json`, `campaign.json`, `asset-<id>.b64`. Change and conflict detection uses the gist's latest commit SHA (`GET /gists/{id}/commits?per_page=1`), stored per device after each pull/push; a full `GET /gists/{id}` (which inlines up to 1 MB per file) only when it changed. If the remote SHA differs at push time, ask: overwrite, load remote, or save a local copy (a duplicate campaign) first. Push in a few batched PATCHes under a byte budget: missing assets first (diffed by hash), then manifest and `campaign.json` together last; delete unreferenced remote assets; honour `Retry-After` and secondary rate limits. Truncated files are fetched from the sha-pinned `raw_url` with a **bare** `fetch(rawUrl)`, no headers at all (gist.githubusercontent.com rejects CORS preflights). Limits: about 7 MB per asset (base64 must stay under 10 MB) and at most ~290 synced assets (the API lists 300 files per gist); a top-level `truncated` gist is an explicit error. The history dialog lists commits and loads a revision lazily, labelling revisions without a matching `campaign.json`. Local zip backup (fflate) holds `campaign.json` plus asset blobs; SPEC §9's zip round-trip e2e is an M8 done-criterion.
- **Testing.** Pure logic (`src/geometry`, `src/projection`, migrations and validation, upload planning, autosave scheduling, initiative sorting, gist serialization with a mocked API) is unit-tested in Node; the stores and actions too (`src/store/*.test.ts`, zustand works without React), and IndexedDB code with `fake-indexeddb` (`src/persistence/db.test.ts`). `src/architecture.test.ts` guards the module boundaries. Playwright smoke tests run against a fresh production build and fail on any console error, including CSP violations. Canvas e2e tests (`e2e/canvas.spec.ts`) drive the real mouse and keyboard and read node positions through `window.Konva` (Konva registers itself there). `e2e/library.spec.ts` covers autosave and reload, scenes, uploads (images generated by `e2e/png.ts`, a dropped 9000 px map), asset deletion, campaigns and the two-tab takeover; every test gets a fresh context, so IndexedDB starts empty.

## Conventions

- TypeScript strict plus `noUncheckedIndexedAccess`, `noImplicitOverride`, `noImplicitReturns` (both tsconfigs). Lint forbids `any` and non-null assertions (`typescript/no-explicit-any`, `typescript/no-non-null-assertion`); justify any inline disable with `// oxlint-disable-next-line <rule> -- reason`.
- Lint-enforced boundaries (`.oxlintrc.json` overrides; they see direct imports only, `src/architecture.test.ts` covers the transitive graph):
  - `src/geometry/**` and `src/projection/**`: no React, Konva, zustand, `idb` or lucide (including subpaths), and no app modules except `src/state`. No `.tsx` files there.
  - `src/player/**` and `src/canvas/**`: no `dm`, `panels`, `tools`, `gist`, `store`, `app/App`, or `persistence` except `persistence/assetBlobs`; `src/canvas/**` also no zustand.
- Styling: Tailwind v4, configured in CSS (`src/styles/index.css`; there is no `tailwind.config.js`). Use the semantic tokens `bg-bg`, `bg-surface`, `bg-surface-2`, `bg-surface-3`, `border-border`, `text-fg`, `text-fg-muted`, `text-accent`, `bg-accent`/`text-accent-fg`, `text-danger`, `text-ok`, `outline-focus`; no raw palette colors in the DM UI. Keep text at WCAG AA contrast (4.5:1). The player window is always black (`html[data-view='player']`).
- Icons: `lucide-react`. Icon-only buttons have `aria-label` and a `title` that includes the shortcut. Hidden and locked states use icons as well as color.
- Network: none at runtime except the GitHub API and gist raw URLs. The production CSP (`vite.config.ts`) enforces it; see Decision 6 for the full policy. When a feature needs another source (for example an image from another origin), change the CSP and its e2e test deliberately.
- Device preferences (theme, player zoom lock `vtt:lockedCellPx`, later the remembered PAT) never go in `CampaignState`, so they don't travel with gists or backups. localStorage keys use the `vtt:` prefix.
- Tests are colocated as `*.test.ts(x)`; they run in Node by default. Add `jsdom` and `// @vitest-environment jsdom` only for files that need a DOM. Use `toStrictEqual` for data (it catches `undefined` keys).
- Commit at the end of each milestone, on that milestone's branch.

## Decisions

Choices where the spec was ambiguous, incomplete or in conflict with a technical constraint. Sections marked "implemented" are built; data-model decisions hold from milestone 1; "Later milestones" is the plan and may be revised (record the revision here) when its milestone is built. Numbers are stable: new decisions get the next free number.

### Milestone 1 (implemented)

1. **Deploy branch is `master`.** The spec says `main`; this repository only has `master`. Build and deploy jobs run only for `refs/heads/master`.
2. **One workflow for CI and deploy.** Typecheck, lint, format check, unit tests and e2e tests run on `master`, milestone branches, PRs and manual runs, and gate the Pages build.
3. **Base path.** `BASE_PATH` env var; CI passes `actions/configure-pages`' `base_path`, which also handles user sites and custom domains. It defaults to `/combat-map-sharing/` locally too, so dev matches production.
4. **Routing.** A ~30-line hash router (`parseHash` + `useSyncExternalStore`) instead of react-router. An empty hash opens the DM view and rewrites the URL to `#/dm`. Each window is a lazily loaded chunk.
5. **Styling.** Tailwind v4 (the spec allowed Tailwind or CSS modules) with CSS-variable theme tokens. Dark by default. The theme is a per-device preference in localStorage, applied before first paint by a small inline script, which also makes the player window black from the first frame.
6. **Content-Security-Policy** in production builds (a `<meta>` tag right after `<meta charset>`; Pages cannot send headers): `default-src 'self'`; `script-src 'self'` plus the hash of the inline theme script (newlines normalized); `style-src 'self' 'unsafe-inline'`; `img-src 'self' blob: data:`; `font-src 'self'`; `connect-src 'self' blob: data: https://api.github.com https://gist.githubusercontent.com`; `worker-src 'self' blob:`; `object-src 'none'`; `base-uri 'self'`; `form-action 'none'`. It enforces the "no runtime network" constraint mechanically. Not applied in dev, because Vite's dev server injects inline scripts.
7. **Linting.** oxlint (the current Vite template's default) with the React, jsx-a11y, import and Vitest plugins, warnings denied, plus Prettier. `react-in-jsx-scope` (obsolete with the automatic JSX runtime) and `jsx-a11y/prefer-tag-over-role` (it would require `<output>` for status messages) are off.
8. **Fonts and icons.** System font stacks, since web fonts would be a runtime network call. Icons from `lucide-react` (ISC license).
9. **UI language is English,** like every UI string in the spec.
10. **The whole stack is installed in M1,** so later milestones start from pinned, mutually compatible versions.
11. **The player window title is the generic "Player view".** It is visible on the shared screen, so it must not show campaign or scene names.
12. **Secure context required.** The app refuses to start over plain http on a non-localhost address, because `crypto.randomUUID`, `crypto.subtle` and Web Locks need a secure context.

### Data model (refinements of SPEC §4)

13. **Items are center-anchored,** rotating about the center. This makes snapping footprints to cell centers and rotating with the Transformer straightforward.
14. **Pings are transient.** They, the live ruler, temporary templates, selection and the DM camera live in transient `UiState`, not in `Scene` (the spec's `Scene.pings` is marked transient anyway).
15. **No optional keys in persisted data.** Optional values are explicit `null`, and the state is plain JSON throughout. Stable shapes make migrations, Immer patches and gist round-trips predictable.
16. **Initiative refinements:**
    - `activeEntryId` replaces `currentIndex`, so editing values or re-sorting cannot move the turn;
    - `manualOrder` holds the drag-and-drop tiebreak;
    - `visibility: 'auto' | 'hidden' | 'shown'` implements "hidden tokens' entries are hidden automatically, but can be unhidden separately". `'auto'` follows the token (missing, hidden or on a hidden layer = hidden), not its fog visibility;
    - entry names are player-facing: created from the token's label when shown, otherwise its name, and editable;
    - `Token.initiativeModifier` stores the per-token modifier for "roll for selected enemies".
17. **Built-in assets are not in `library`.** They live in a code registry (`builtin:` ids); `library` holds uploads only, which are the only assets synced to gists. Built-in "initials" tokens draw `Token.badge`.
18. **Undo-exempt state lives outside `scenes`.** Explored fog memory and the pushed player view are in `CampaignState.sceneMemory`, because Immer records scene splices (reorder, duplicate, delete) as whole-element replaces: undoing one would otherwise roll them back. Explored memory is never undone because players have already seen it.
19. **Explored fog storage.** A sparse map of 64×64-cell chunks at a quarter-cell resolution, base64 per chunk with trailing zero bytes omitted, so it works on an unbounded canvas and is already compact for the gist. Manual fog edits are undoable.
20. **Manual fog edits apply in order on top of automatic fog.** `reveal` makes an area fully visible, including the tokens in it; `hide` makes it black.
21. **Layer visibility hides a layer from players too,** so "hidden" means the same thing everywhere. Hidden tokens are not vision sources; to reveal an area without showing a token, use a manual reveal.
22. **Presentation is campaign-level and not undoable,** except the player zoom lock ("1 cell = N px"), which depends on the physical display and is a device preference. Shared views are world rectangles (`ViewRect`) fitted to the player's screen, so a pushed or followed view shows the same area on any screen size. 'fit-explored' frames explored ∪ visible areas, or the map layer bounds when fog or explored memory is off.
23. **NPC vision** ("optionally allow it on NPC allies") is a campaign setting, `npcVision`; NPCs only reveal fog when their `visionFt` is set.
24. **Players see only the fraction of public HP,** never the numbers, on tokens and in the tracker. Token `kind` is never sent.
25. **Default grid size is 70 world px,** a common VTT default. The DM calibrates it to each map.
26. **Token size follows the grid.** Width/height = footprint × grid size, rewritten on calibration and size-category changes; tokens are rotated, not resized, with the Transformer.

### Later milestones (planned)

27. **Sync sends throttled full snapshots, no diffs (M4).** The projection carries asset ids, not blobs, so it stays small; a fog revision lets the player skip re-rasterizing unchanged fog.
28. **Presence and the single DM window use Web Locks (M3/M4),** not heartbeat timers, which background tabs throttle to once a minute.
29. **Token visibility in fog uses nine sample points of the footprint (M5),** so a large creature that is partly in view is shown.
30. **Assets are finalized at import (M3).** Downscaling and re-encoding happen when the file is imported, so the stored blob is exactly what is synced and `AssetMeta.hash/mime/bytes` stay true on every machine.
31. **Gist asset size limit is about 7 MB (M8).** Base64 inflates files by 4/3 and gist files over 10 MB cannot be fetched through the API, so an asset must be under about 7.5 MB before encoding; the spec's ~8 MB would exceed 10 MB once encoded. Larger assets stay local-only (`localOnly: true`). A gist also lists at most 300 files, so at most ~290 assets sync.
32. **Gist conflicts compare commit SHAs, not `updated_at` (M8),** and API GETs bypass the browser cache. "Save a local copy first" duplicates the campaign locally.
33. **Gist connection data and the PAT are device-local (M8).** The gist id, last synced commit SHA, auto-sync settings (interval, last pushed hash) and the token live in the IndexedDB `meta` store, not in `CampaignState`, so they are never written into the gist or into exports.
34. **Shared origin (M8).** Every GitHub Pages project site of an account shares the origin `https://michelepapucci.github.io`, so any other site published there can read this app's IndexedDB (including a remembered PAT) and its BroadcastChannel. The token UI recommends a fine-grained token with only the Gists permission and an expiry date, and says that "Remember token" stores it readable by other sites on the same origin. A custom domain for this repository would remove the issue (only `DEFAULT_BASE` and the Playwright base would change).

### Milestone 2 (implemented)

35. **Drags are custom pointer gestures, not Konva `draggable`.** Konva's Transformer moves the other selected nodes by the raw pointer delta, which breaks snapping for multi-selections. Here the grabbed item snaps and the rest of the selection moves by the same snapped delta, and `ui.liveDrag` (needed by the player sync in M4) is the single source of live positions. A press becomes a drag after 4 screen px; otherwise it is a click.
36. **Snapping refinements.** Nearer-edge snapping (see Coordinates) also handles props that are not a whole number of cells. Placement from the library always snaps (when snapping is on), drags snap as in Decision 48, arrow nudges move exactly one cell or one px. Paste is moved by whole cells. A map placed by clicking in an empty map layer goes to the grid origin and the view fits it; a dropped map is centered on the drop point with its top-left corner snapped to an intersection.
37. **Locks.** A locked item can be selected (to unlock, hide, duplicate or reorder it) but is never moved, transformed, nudged or deleted; the canvas shows a dashed outline and a lock badge instead of the Transformer, and deleting explains why. Items on a locked or hidden layer cannot be picked at all; locking or hiding a layer deselects its items. The marquee selects only movable items, so it never grabs the (locked) map.
38. **Layer visibility hides the layer in the DM window too** (Decision 21 hides it from players). Hidden items show at half opacity with an eye-off badge.
39. **Token presets and badges (refines Decision 17).** The Tokens tab offers presets (Hero, Ally, Goblin, Skeleton, Bandit, Guard, Wolf, Noble, Ogre, Fire elemental, Giant, Dragon) over seven stable token assets (`builtin:token/initials` and six glyphs). New tokens take the color of their kind (blue players, green NPCs, red enemies) unless the DM picks a palette color. Initials tokens draw `badge` as their text; glyph tokens draw it as a small number pip. Badges are automatic ("Orc Captain 2" → "OC2", glyphs: "2") and follow renames and renumbering while they still match the automatic value; a badge the DM typed is kept.
40. **Auto-numbering applies to every token, from 1.** Placing, duplicating or pasting "Goblin" or "Goblin 3" creates "Goblin N" with N one above the highest number in the scene.
41. **Copy/paste/duplicate.** Paste goes under the pointer when it is over the canvas (moved by whole cells, so alignment is kept), otherwise one more cell down-right per paste; duplicate is one cell down-right. Copies go on top of their layer and become the selection. Tokens are resized to the current scene's grid.
42. **Context menu and properties in M2.** "Add to initiative" arrives with the tracker (M6). "Edit token" focuses the name field of the properties panel. The M2 properties panel edits name, kind, size category, badge, color, rotation and opacity, plus hide/lock/order/duplicate/delete; vision, HP, conditions, label and notes come in M5. With nothing selected the panel shows the scene's grid settings, including "Calibrate".
43. **Size changes.** A new grid size resizes token footprints keeping their centers (the DM re-snaps if needed). A new size category keeps the token's top-left corner, so an aligned token stays aligned. Calibration uses the mean of the box's width and height divided by N, and normalizes offsets to `[0, size)`.
44. **Built-in maps** are 1680 × 1260 px (24 × 18 cells at 70 px) with no grid drawn on them.
45. **Shortcut refinements.** Redo also on Ctrl+Y, delete also on Backspace, ⌘ instead of Ctrl on macOS. Shortcuts are ignored while typing in fields (range inputs keep their arrow keys) and during a drag. Esc cancels a gesture first, then the tool, then the selection. Mouse clicks don't leave focus on buttons, so Space-to-pan never presses the last clicked button. Tools from later milestones (M, A, F, P) are visible but disabled, with the milestone in the tooltip.
46. **View.** Zoom 5 %–800 %; the wheel (and trackpad pinch) zooms toward the pointer. Zoom controls in the corner: out, reset to 100 %, in, fit everything. A right-drag pan never opens the item menu on release (Windows fires `contextmenu` on mouse-up).
47. **Notices before toasts.** A one-line status message at the bottom of the canvas (calibration result, locked items, copy) stands in until the toasts of M9.
48. **Tokens always snap; props snap magnetically.** SPEC §5.1 puts "the snap is magnetic (~25% of a cell)" in the props bullet under a "Magnetic snapping" heading, so it is ambiguous for tokens. Magnetic token drags left a token off the grid whenever it was dropped more than a quarter cell from alignment (about half of all drops), which breaks cell counting in combat. With snapping on, a dragged token always lands on its cells (odd footprints on centers, even ones on intersections); props keep the 25% magnet. Alt still gives free placement for both.

### Milestone 3 (implemented)

49. **The validator rejects bad types and repairs benign inconsistencies.** Type errors, unknown enum values, non-finite numbers, non-hex colors, duplicate ids, over-long ids and malformed fog chunks reject the whole document (`CampaignValidationError` with a path such as `scenes[0].layers.tokens[2].hp.max`). Harmless inconsistencies are repaired and listed: over-long free text (names, labels, notes, tags, conditions) shortened, since anything the editor can save must load again (`src/store/roundtrip.test.ts` runs random editing sessions and checks exactly that; the editor also caps names at 200 characters, numbering included); grid offsets and rotations normalized, token sizes rewritten from their size category, dangling `activeSceneId`/`activeEntryId`/`splashAssetId` reset, missing scene memory created, orphan memory and empty fog chunks dropped, duplicate conditions removed. An initiative entry whose token was deleted keeps its `tokenId` ('auto' visibility then hides it). Ids may not name `Object.prototype` members, so a scene id cannot be `__proto__`.
50. **Scene memory outlives its scene until the next load.** Deleting a scene keeps its `sceneMemory` entry, so undoing the delete restores the explored fog too; the validator drops orphans on load, when history is gone anyway. A recorded recipe may also change unrecorded fields (a new scene's memory, `activeSceneId`): the change applies and is never undone.
51. **Undo shows where the change happened.** History entries record the active scene before and after; undo switches to `sceneBefore`, redo to `sceneAfter` (when they exist), so undoing a change made in another scene is never invisible and undoing "Delete scene" lands on the restored scene. Switching scenes is not an undo step, and history never merges (coalesces) changes made in different scenes. The DM camera is remembered per scene for the session; a scene not seen yet is fitted to its content.
52. **Asset blobs are shared between local campaigns.** Duplicating a campaign copies only its JSON. A blob is deleted when nothing lists it: after deleting an asset or a campaign, and at startup (which also cleans blobs left by an upload interrupted before its library entry was saved). The collection runs in one IndexedDB transaction over campaigns and assets and counts the open campaign by its in-memory library (its stored record may be stale when the disk is full, and deleting images is how the DM frees space), plus uploads in progress.
53. **Deleting an uploaded asset** asks for confirmation and says how many items in how many scenes use it. Confirming removes those items in every scene, the splash image and clipboard entries that use it; undo history is cleared when items were removed or when the history mentions the asset (undo could otherwise bring back items without an image).
54. **Where uploads go.** Image files dropped on the canvas (or uploaded from the empty state) are maps, placed at the drop point (the first map of an empty scene at the grid origin, with the view fitted). Uploads from the library (button or drop on the panel) become assets of the open tab's kind, without placing them; the notice names the kind, and a single uploaded image opens in the asset dialog to set its name, tags and defaults. Imports run one file at a time with a progress notice (Upload buttons disabled meanwhile), and belong to the campaign they started in. An uploaded token defaults to a medium enemy: a wrong guess then hides a token from the fogged player view instead of revealing fog (player tokens are vision sources). Kind, default size/kind/footprint, name and tags can be edited later; they apply to new placements. Tags are lowercase; search matches names and tags.
55. **Upload finalization.** Files over 100 MB or not PNG/JPEG/WebP (by magic bytes) are refused with a reason. An image within 8192 px and 7 MB is stored byte for byte. Otherwise it is re-encoded as WebP at quality 0.92, 0.85, 0.75, 0.6 until it fits; browsers that cannot encode WebP fall back to JPEG for maps and PNG for tokens and props. If nothing fits, the asset is `localOnly`, keeping the original file when it did not need downscaling and the best-quality encoding otherwise. EXIF orientation is applied when decoding, so stored dimensions match what is drawn. Thumbnails (256 px) are stored separately and regenerated if missing.
56. **Uploaded token images** are cropped to a circle (88 % of the radius) inside a disc of the ring color, with the badge as a number pip like glyph tokens.
57. **A second DM tab is inactive, not read-only** (refines Decision 28 and the M3/M4 plan): it shows "already open in another tab" instead of a frozen copy that could go stale. "Use this tab instead" asks the other tab to save and hand over, and steals the lock after 3 s if it does not answer. At startup a tab waits up to 1 s for the lock, so reloading does not trip over the page being unloaded. Losing the lock bumps a session epoch that every asynchronous session step re-checks after each `await`, and saving refuses without the lock, so a tab that is taken over mid-load can never show or save the campaign. If the old tab could not save its last changes, the new one says so. Known limit: if the old tab's save hangs for more than 3 s and the lock is stolen, that save may still land after the new tab has loaded.
58. **Unsaved changes ask before leaving.** IndexedDB writes started while a page unloads are aborted, so autosave cannot rescue the last second of work on reload or close. When the status is not "Saved" (an edit in the last second, or a failed save), leaving shows the browser's "Leave site?" prompt; the save is flushed at the same time. A failed save keeps the indicator red ("Not saved, retry", announced as an alert) until a save succeeds, and its first failure shows a message that stays until dismissed. Ctrl+S saves at once (gist sync takes the shortcut over in M8).
59. **Local campaigns** live in the Campaigns dialog (the campaign name in the header): rename the open one (undoable, `name` is recorded), create, open, duplicate ("(copy)"), delete with confirmation. Deleting the open campaign opens the most recently saved other one, or a new one. The app reopens the last opened campaign. Opening another campaign first saves the open one, and stays put if that save fails.
60. **Settings dialog (M3 contents):** the diagonal rule (used by drag distances now, the ruler in M7) and storage: usage estimate, persistent-storage status with a button to ask again, and the count of local-only images.
61. **Scene tabs above the canvas.** Click to switch, double-click (or ⋯ → Rename) to rename, ⋯ to duplicate, move left/right or delete (confirmation; undoable). New scenes are named "Scene N" and inserted after the active scene; duplicates get new ids for every item, fog edit, initiative entry and template, keep initiative links, and copy the explored fog and pushed view.
62. **If IndexedDB is unavailable** (blocked storage, broken profile) the DM still gets a working session in memory, with a red "Not saving" indicator.
63. **Decoded images are reference-counted with a budget.** Images shown by a mounted component are never evicted; idle ones are kept up to 64 Mpx (about one 8k map, 256 MB) and evicted least recently used first, with `ImageBitmap.close()`. Eviction runs after the current task, so a scene switch that unmounts and remounts the same map never sees it closed.
64. **Notices before toasts, refined.** Short confirmations fade after 3.5 s; warnings and errors (upload problems, a failed save) stay until dismissed. The DM window shows "Opening your campaign…" while the session starts (after a short delay, so fast loads show nothing).
